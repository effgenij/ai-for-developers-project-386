# E2E Booking Scenarios Design

## Goal

Add browser-level integration checks that verify the calendar booking application works end-to-end with the real frontend and backend running together.

## Scope

- Cover the main booking flow in a real browser.
- Cover the full UI path from admin setup to guest booking to admin verification.
- Add CI execution for the browser tests.
- Keep the existing autogenerated `hexlet-check.yml` untouched.

## Recommended Approach

Use Playwright Test with two local web servers started by Playwright itself:

- frontend: Vite app on `http://127.0.0.1:5173`
- backend: Fastify app on `http://127.0.0.1:3000`

This keeps the tests close to the real user experience while still allowing targeted data setup through backend API calls where that makes the suite faster and more stable.

## Test Layout

Store the e2e tests inside the frontend app:

- `apps/frontend/e2e/admin-to-booking.spec.ts`
- `apps/frontend/e2e/booking-flow.spec.ts`
- `apps/frontend/e2e/helpers/` for shared setup and browser helpers
- `apps/frontend/playwright.config.ts`

This keeps Playwright configuration and test ownership aligned with the application entry point being exercised.

## Runtime Model

Playwright config will:

- use `baseURL: http://127.0.0.1:5173`
- start multiple `webServer` processes:
  - `npm run dev --workspace @repo/backend`
  - `npm run dev --workspace @repo/frontend`
- set `reuseExistingServer: !process.env.CI`
- set `workers: 1` in CI for stability
- save traces on failures or retries to simplify debugging

The frontend continues to use its Vite proxy, so browser traffic stays on `/api/...` and reaches the backend naturally.

## Scenarios

### 1. Full Path: Admin Creates Event Type, Guest Books, Admin Sees Booking

File: `apps/frontend/e2e/admin-to-booking.spec.ts`

Flow:

1. Open `/admin/event-types`.
2. Create a new event type through the admin drawer.
3. Verify the new event type card appears.
4. Open `/book`.
5. Choose the newly created event type.
6. Select a day and a free slot.
7. Continue to guest details.
8. Submit guest name and email.
9. Verify the success screen.
10. Open `/admin/bookings`.
11. Verify the created booking is listed.

What it proves:

- admin UI can create data through the real backend;
- guest booking works against that real data;
- backend persists the booking;
- admin UI reads the same persisted state.

### 2. Guest-Only Happy Path

File: `apps/frontend/e2e/booking-flow.spec.ts`

Flow:

1. Create an event type through a backend API helper before navigation.
2. Open `/book/:eventTypeId` directly.
3. Select a slot.
4. Continue to guest details.
5. Submit guest name and email.
6. Verify the success screen shows the confirmed booking.

What it proves:

- the core guest flow remains covered independently from admin UI;
- the suite has a faster smoke-style path for the most critical user journey.

### 3. Occupied Slot Is Not Offered

Also placed in `apps/frontend/e2e/booking-flow.spec.ts`.

Flow:

1. Create an event type through backend API helper.
2. Create a booking through backend API helper for a specific future slot.
3. Open the booking page for that event type.
4. Verify the occupied slot is not shown in the slot list.

What it proves:

- backend booking constraints surface correctly in the real UI;
- the application does not offer already occupied time slots.

## Assertions And Locator Strategy

Prefer stable user-facing locators:

- `getByRole(...)`
- `getByLabel(...)`
- visible text and button names

Avoid brittle selectors tied to internal Mantine DOM structure.

Add `data-testid` only if a critical interaction cannot be made stable with semantic locators.

Key assertions:

- event type appears by name in admin and booking catalog
- slot selection and step transitions work
- success screen contains confirmation text, event name, guest name, and email
- admin bookings page contains the created booking
- pre-occupied slot is absent from available slot choices

## CI Design

Add a dedicated workflow: `.github/workflows/playwright.yml`

Pipeline shape:

1. Checkout repository
2. Set up Node.js 22
3. Run `npm ci`
4. Run `npx playwright install --with-deps`
5. Run `npx turbo run test:e2e --filter=@repo/frontend`
6. Upload Playwright artifacts such as `playwright-report/` and `test-results/`

Triggers:

- `pull_request` targeting `main`
- `workflow_dispatch`
- optionally `push` to `main`

## Turborepo And Scripts

Add package-level frontend scripts:

- `test:e2e`
- `test:e2e:headed`

Register `test:e2e` in `turbo.json` so CI and local runs use a normal package task instead of ad-hoc root logic.

Optional convenience wrappers may be added in `mise.toml` and the root `package.json`, but only as thin delegations to `turbo run test:e2e`.

## Branch Workflow

Before starting implementation, local `main` must be synchronized with `origin/main`, then the feature branch is created:

1. `git fetch origin`
2. `git switch main`
3. `git pull --ff-only origin main`
4. `git switch -c feat/e2e-booking-scenarios`

This branch workflow has already been executed for this task.

## Completion Criteria

The step is complete when all of the following are true:

- Playwright tests cover the approved scenarios.
- Tests run in a real browser against the real frontend and backend.
- Servers are started automatically by Playwright.
- CI runs the e2e suite on pull requests.
- Failing CI runs preserve Playwright artifacts for debugging.
